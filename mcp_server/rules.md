# Mobile Testing Mindset (Lunatap Integration)

## Two modes: harness and handoff

- **Harness mode** (`mobile_observe`, `mobile_act`, `mobile_do_step`, `mobile_wait_for`, `mobile_assert`, `mobile_logs`, `mobile_net`, `mobile_flow`, `mobile_walkthrough`, `mobile_release_device`): you are the planner and the operator. Lunatap runs no model of its own; it observes (the numbered element list from the accessibility tree plus OCR), acts, refuses a tap when the screen moved since you looked, settles simple steps by text match or a cheap decision model, and verifies that the next screen names the step. Use it for anything you are doing interactively: exploring an app, reproducing a bug, walking a flow to write a test. Each call returns in seconds and includes the new screen, so you rarely need a separate observe. Release the device when you are done; while a harness session holds it, handoff tasks on that device are refused, and vice versa.
- **Evidence, checks and flows (harness mode)**: start `mobile_logs(action="start", bundle_id=<app>)` before you reproduce anything; every `mobile_act` reply then names its step and how many log lines the app wrote during it, and `mobile_logs(action="read", since_step=N, grep="error|403")` returns exactly those lines, so a failing step carries its own evidence. Use `mobile_assert(text, state="present"|"absent")` for anything the screen *should* say; a FAIL returns the screen. For a path you will test again on the next build, `mobile_flow(action="record", name=...)` before the first step and `mobile_flow(action="save")` after the last check; `mobile_flow(action="run", name=...)` (or `lunatap flow run <folder>` in CI) replays it and stops at the first failing step or check. Alerts: an alert on screen names the page, its buttons are listed as `AlertButton`, and `mobile_act(action="alert", text="Allow While Using App")` presses one. Network: `mobile_net(action="start")` runs mitmproxy (must be installed) and returns the one-time device setup; it is a person's job on a phone (Wi-Fi proxy, trust the CA), so relay it verbatim; afterwards each `mobile_act` reply names the requests made during its step and `mobile_net(action="read", since_step=N, failed_only=true)` shows the failing call with the server's own reason. Maps and custom-drawn views: `mobile_observe(detect="markers")` lists the pins in the screenshot as `Marker` elements to tap by index: round pins of any colour (grey with a white ring too), each with a confidence and a kind: `pin` (a plain disc), `icon` (a symbol inside, e.g. a map's park or restaurant POI), or one `cluster of N+` element for touching pins (`N+` is a floor: pins hide under each other). On satellite imagery the reply says so and confidences deserve less trust; confirm with `screenshot=true`. A flow replays against the screen titles it recorded: a step that lands elsewhere fails, and a check that failed while recording is not saved.
- **Walkthrough videos (harness mode)**: to show someone how the app works, `mobile_walkthrough(action="start", name=...)` on the simulator, then walk the path with `mobile_act` / `mobile_do_step` / `mobile_assert` as usual; each becomes a captioned step. Reword a step for the viewer with `mobile_walkthrough(action="caption", text=...)` right after it. `mobile_walkthrough(action="stop")` returns the folder with `walkthrough.mp4` (captioned, ready to share), the screenshots and `steps.md`. Keep detours out: anything you do while it runs is in the video.
- **Handoff mode** (`mobile_run_task` + `mobile_manage_task`): Lunatap's autonomous agent (Flash or Pro, described below) takes a goal and runs it unattended with its own LLM. Use it for long or repetitive workflows you do not want to steer, batch runs, and anything that must run without you in the loop. It needs an LLM key configured in Lunatap's `.env`.

Write executable tests based on device behavior verified with **Lunatap**. Before authoring a test, explore the target application and confirm its screens, transitions, and interactions. Use Lunatap device actions to investigate software and hardware behavior instead of assuming how an interaction works.

### 1. The Runnable Code Principle & Lunatap Exploration
- **When tasked with authoring tests**, deliver runnable test code with verified interactions and explicit wait conditions.
- Before writing any test code, you must use the Lunatap MCP tools to interactively run and explore the target application. This allows you to discover the exact sequence of UI states, transitions, and required interactions.
- Analyze the user's target testing framework to exploit its native capabilities and maximize test stability.
- **Timing & Latency Management (Exploration vs. Execution)**:
  - **Precise Timing in Final Code**: While Lunatap's AI exploration inherently involves model latency and is not strictly time-precise, you must bridge this gap in your final deliverables. Use Lunatap to discover and verify the interaction path, then implement exact, deterministic timing and wait conditions (`sleep`, explicit/implicit waits) in your authored test scripts, as local test execution runs without LLM overhead.
  - **Compensating for Model Latency During Exploration**: When delegating exploratory tasks to Lunatap that involve waiting periods (e.g., waiting 30 seconds for a page load or timer), adjust the requested wait duration in your task description based on the selected model's natural step interval:
    - **Flash Model**: The average processing interval between steps is roughly **5 seconds**. For a required 30-second delay, instruct the agent to wait for approximately **25 seconds**.
    - **Pro Model**: The processing interval between turns is typically **~30 seconds** (due to multi-agent planning and verification). The natural pipeline delay often covers the required waiting time without adding long explicit delay commands.
  - **Pragmatic Timing Judgment**: When a user request mentions performing an action for a specific duration (e.g., "stay on this screen for 2 minutes"), evaluate whether exact timing is functionally critical. Often, these durations are rough guidelines rather than strict test constraints—exercise flexibility and pragmatic engineering judgment to achieve the verification goal efficiently.


### 2. Lunatap Closed-Loop Architecture Mastery
Deeply understand and select between Lunatap's dual execution models (**Lunatap Flash** and **Lunatap Pro**) based on the task scenario, and master their corresponding workflows:

- **Lunatap Flash (Fast / Reactive Model)**:
  - **Applicable Scenarios**: Designed for simple, highly deterministic, lightweight UI operations or direct automation workflows. There is no step cap by default (history is compressed rather than truncated), so task length alone is not a reason to choose Pro; choose Pro when the task needs a persistent plan, verified checkpoints, notes or a written report, or multi-branch exploration.
  - **Execution Mechanism (Reactive Loop)**: Does not enter the LangGraph multi-node orchestration: there is no Planner, no pre-execution safety net, and no Checker. `FlashRunner` receives the user's goal, the latest UI element list, and the live screenshot, performs "Observe-Think-Act" with a single LLM, and calls action tools until it reports the task status. It chains taps into one `click_sequence` to catch transient UI (auto-fading control bars, toasts) before they expire, and it can call `ask_explorer` for element grounding, `search_history` / `replay_steps` / `get_step_screenshot` to look up compressed earlier steps, and `video_analyzer` over the session recording. History lives in the same session transcript ledger as Pro (session-relative `T+mm:ss` clock, screenshots folded into visual summaries, older steps chunked into eras).

- **Lunatap Pro (Deep / Multi-Agent Graph-Driven Closed-Loop Model)**:
  - **Applicable Scenarios**: Designed for long-range, highly complex, dynamic multi-branch tasks; continuous monitoring / polling loops; and tasks requiring deep diagnostics (video analysis), verified checkpoints, or a detailed written report.
  - **Execution Mechanism (Plan-Execute-Verify-Summarize Closed-Loop)**:
    - **Planner**: Deconstructs complex, high-level testing goals into a living Markdown task plan with milestones and `verify` / `assert` check items. Later milestone edits get an advisory review (a hint plus reason back to the Operator; the plan is never rolled back).
    - **Operator**: Consumes the plan, analyzes the current screen state (screenshots plus the UI element list, with the Explorer for grounding at the `explorer_mode` perception depth: `flash` 1-shot, `pro` 3-turn, `ultra` deep zoom), keeps notes, and executes precise device interactions; it can also recall compressed history and analyze the session recording.
    - **Safety Net & Execution Incidents**: A single turn-ending action is vetted by a pre-execution safety net (XML-first, pixel fallback). A multi-action turn is a **fast-action burst** that fires back to back without the safety net, which is how the Operator defeats turn latency on transient UI. When an action is intercepted or fails, the system opens an **execution incident** that persists in the Operator's context (with the consecutive-failure count shown as a fact) until a later action executes successfully; recovery is the Operator's own decision and there is no separate repair agent.
    - **Checker (Verification)**: A read-only verifier with the same observation tools as the Operator audits plan-declared checkpoints and performs an exit final review against the original goal; `verification_level` selects the depth (`off`, `final` = exit review only and the default, `checkpoints` = every checkpoint plus exit review, `strict` = checkpoints with a larger repair budget where a failed assert halts the run).
    - **Outputter (Optional)**: Synthesizes the entire execution trace into a human-readable report detailing every action step and visual result.

### 3. Device & Environment Constraints & Multi-Device Management
- **Device Selection & Multi-Device Execution**: Lunatap supports multi-device execution and per-device concurrency. You can control device targeting via two modes:
  - **Direct Device Specification**: Provide the target device's UDID (a simulator or a paired iPhone/iPad) via `device_serial` to `mobile_run_task` or `mobile_get_device_state`. Tasks targeting distinct devices run concurrently without blocking each other.
  - **Automatic Device Selection**: When `device_serial` is omitted, Lunatap uses the single booted simulator. Physical iPhones/iPads are never selected automatically; pass their UDID.
- **Prioritize User Choice for Device Selection**:
  - When several simulators are booted, a phone is attached, or device selection is otherwise ambiguous, **YOU MUST PRIORITIZE ASKING THE USER** to select or confirm their preferred device before launching a task.
- **Listing Devices**:
  - Use `xcrun simctl list devices` (simulators: UDID, name, Booted/Shutdown) and `xcrun devicectl list devices` (paired iPhones/iPads and their connection state) via bash to find UDIDs and troubleshoot device issues.
- **Files & Logs**: Lunatap operates within the device boundary. To pull files or logs from a device to the Mac, use the Apple tools directly (for example `xcrun simctl get_app_container <UDID> <bundle-id> data`, `xcrun simctl spawn <UDID> log show`, or `xcrun devicectl device copy from ...`).
- **Prerequisites**: macOS with Xcode 15 or later, and a simulator (booted, or one whose UDID you pass; Lunatap boots it) or a paired iPhone/iPad with WebDriverAgent installed (see `docs/ios.md`).
- **Per-Device Mutual Exclusion**: Lunatap manages per-device execution mutexes (`DeviceExecutionLock`). A device can only execute a single task at a time (FIFO queue), while different devices can execute tasks in parallel.

### 4. Robust Test Code Design (The "Dynamic-First, Coordinate-Fallback" Philosophy)
*If your task involves authoring test code, you must adhere to the following design principles for maximum reliability:*
- **Adapt to Framework Capabilities**: You must first assess what locating mechanisms the user's test framework supports (e.g., accessibility identifiers, labels, XCUITest queries, OCR, image template matching, or absolute/relative coordinates).
- **The Core Principle: Dynamic-First, Coordinate-Fallback**:
  - Wherever supported by the framework, **always prioritize dynamic element locating** (using IDs, text, OCR, etc.) to ensure the test code can withstand UI layout drifts and resolution changes.
  - Use **absolute coordinates as a reliable fallback** to guarantee execution success when dynamic locators fail or are unavailable.
- **Implementing Resilient Locating Patterns**:
  - **Dual-Capable Frameworks**: If the framework supports both dynamic and coordinate-based locating, implement the **Try-Catch Fallback Pattern**:
    1. **Try**: Attempt to interact with the element using dynamic locators (IDs, OCR, text) for maximum resilience against UI changes.
    2. **Catch**: If the dynamic attempt fails, fall back to the precise absolute coordinates verified during your Lunatap exploration.
  - **Coordinate-Only Frameworks**: If the framework only supports coordinates, ensure the coordinates are well-documented, and where possible, parameterized or made relative to screen boundaries to mitigate resolution differences.
  - **Dynamic-Only Frameworks**: If the framework does not support coordinate-based clicks, focus entirely on generating highly robust dynamic locators, leveraging Lunatap's element descriptions and XML tree analysis.

### 5. Environment Self-Diagnosis (`mobile_diagnose`)
- **Diagnose before guessing**: Whenever an Lunatap tool returns an error, a task fails to start or is rejected, no device is found, or the user reports that Lunatap "doesn't work" in the IDE, call `mobile_diagnose` first. Do not troubleshoot by re-running `mobile_run_task` on trial and error, and do not ask the user to run device commands by hand before you have the report.
- **If `mobile_diagnose` is not in your tool list at all**, the MCP server itself failed to start: check the IDE's MCP server log and run `uv run lunatap doctor` in the project directory (the CLI shares the same checks).
- **Follow `next_steps` in order**: The report lists fixes in dependency order (Python runtime → config → MCP host → LLM credentials → device → optional video toolchain). `Run:` lines are single, local, non-destructive shell commands (one command per line, no `&&`) you may execute yourself (ask before installing software with winget / brew / apt). `Guidance:` lines describe something only the user can do (unlock the phone, trust the developer certificate, plug in a cable, free a port, tell you which IDE they use) — relay them verbatim. `Docs:` lines are references.
- **Let Lunatap self-heal first**: Call `mobile_diagnose(attempt_fix=true)` before asking for manual intervention; it removes stale device locks / queue tickets left behind by crashed runners.
- **Deeper checks on demand**: `verify_credentials=true` validates the configured API keys live (~12s; use when a key exists but tasks fail with auth / quota errors; result in `credentials`). `probe_device=true` runs a true end-to-end check — screenshot plus UI hierarchy through WebDriverAgent or Xcode's device tools (~20s; use when the device shows connected but observation or tasks fail; result in `device_probe`).
- **Physical iPhones**: the `ios_wda_signing` check reads the WebDriverAgent runner's signing profile (a free team's expires every 7 days). Expired plus a physical `device_serial` means `blocked`, with the exact re-sign command under `Run:`. When a WDA launch fails anyway, the error names the cause in `[cause: ..., ...]`: `wda_profile_expired` and `wda_signing_missing` are fixed on the Mac (the command is in the message); `wda_cert_untrusted` (Settings > General > VPN & Device Management > Trust), `device_locked` and `ui_automation_disabled` need the person holding the phone, so ask them straight away. A simulator's WDA answering for the phone (`isSimulator=True`) means release the simulator session the error names. `logs.device_log_capture` says which log sources `mobile_logs` can use here.
- **Busy devices**: `tasks: {active, queued}` lists tasks currently holding or waiting for devices. A busy device means wait, or stop the task with `mobile_manage_task(action="stop", trace_id=...)`.
- **Credentials never go through the chat**: If the LLM key is missing, ask the user to add it to the `.env` file at the path the report shows (`host.env_file`) or to the MCP server's `env` block, then to restart the MCP server. `lunatap init` is interactive and cannot be driven from a tool call.
- **Restart after configuration changes**: Settings are read when the server starts. After editing `.env`, `config/artemis.jsonc`, or the MCP client configuration, reload the MCP server in the IDE before calling `mobile_diagnose` again; otherwise it reports the old state.
- **Failed tasks**: `logs.last_failed_task` gives the trace id, its `stderr_log`, and `recent_errors` (the error lines from that stderr, so you need not open the file); read them before re-running the task. Repeat `mobile_diagnose` until `verdict` is `ready` or `degraded` before delegating tasks again (`degraded` means tasks can run but something optional is off: ffprobe for recordings, the OCR key, a secondary credential, or a host warning such as an interpreter mismatch or a squatted daemon port; relay its `[OPTIONAL]` steps to the user, do not loop on them).
