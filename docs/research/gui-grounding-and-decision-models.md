# GUI grounding on mobile and small decision models: what the evidence says

Research memo for the Lunatap design review, 2026-11-09. Question: is a Jev/Clef-style small decision model that
picks from an indexed element list (XCUITest tree + Vision OCR) a sound grounding design, compared with what the
field does? Every number below comes from the cited primary source; where sources disagree or are not comparable,
it says so. "Fetched" means the page was read for this memo; a few items that could not be read are listed at the end.

## Summary

1. "LLM picks an element by index from a list built from the a11y tree" is the mainstream, best-tested mobile design: AndroidWorld's M3A (30.6%) and SeeAct's "textual choices" both beat Set-of-Mark/pixel variants of the same model ([AndroidWorld](https://arxiv.org/html/2405.14573), [SeeAct](https://arxiv.org/html/2401.01614)).
2. Its known ceiling is the list, not the chooser: elements missing from the tree, icons without text, and scrolled-off targets dominate error analyses ([UGround](https://arxiv.org/html/2410.05243), [ScreenSpot-Pro](https://arxiv.org/html/2504.07981)).
3. Dedicated 2B–7B grounding models now reach 89–94% on ScreenSpot-v2 and run locally; frontier agents (UI-TARS-2, Claude, CUA) ground by pixel coordinates from the screenshot and are far ahead end-to-end ([UI-TARS](https://arxiv.org/html/2501.12326), [UI-TARS README](https://github.com/bytedance/UI-TARS)).
4. Clef/Jev are explicitly "decision" models: typed Choice/Noul/Score questions with per-option probabilities. Cloudflare's Clef has no Box type; Jev 1.14's Box is "preview" ([clef-flash](https://developers.cloudflare.com/workers-ai/models/clef-flash/), [Box](https://docs.typesafe.ai/primitives/box.md)).
5. Using Clef as the *chooser over a list* is within its design envelope; using it as a *grounder over pixels* is not. The vendor's own caveats (first-option bias, distractor-sensitive, confidence is not P(correct)) map directly onto the risks of a long element list ([jaggedness](https://docs.typesafe.ai/model-jaggedness.md), [confidence](https://docs.typesafe.ai/confidence.md)).
6. No published evaluation of Clef or Jev on GUI screenshots exists; Lunatap's 38/40 internal figure is the only datapoint and is too small to rank it against the table below.
7. The sound design is a cascade: cheap list-choice first, with the list pre-filtered; a verifier/companion question; and a local visual grounder (not the LLM) as the fallback for off-tree targets. That is what Agent S2, ScreenSeekeR and OmniParser-style hybrids do, with measured gains ([Agent S2](https://arxiv.org/html/2504.00906)).
8. Speed claims ("193.6x faster") are marketing charts; the engineering gain is real but should be measured per step on Lunatap's own traces ([typesafe.ai](https://typesafe.ai/)).

## 1. Set-of-Mark prompting and the mobile agents that use it

- **Set-of-Mark (SoM)**, Yang et al., Oct 2023: segment the image with SEEM/SAM, overlay alphanumeric marks, and let GPT-4V answer by mark. The abstract reports only that zero-shot GPT-4V+SoM beats the fine-tuned RefCOCOg state of the art; no GUI numbers ([arXiv 2310.11441](https://arxiv.org/abs/2310.11441)).
- **SeeAct** (Mind2Web, web) compared three groundings for GPT-4V. Step success (cross-task/-website/-domain): element attributes 16.1/12.1/19.0; image annotation (SoM) 20.3/13.9/23.7; **textual choices 39.1/32.7/42.0**; oracle 61.9/65.0/62.1. Of 100 SoM errors, ~54% were hallucinated boxes/labels and ~46% a correct box linked to the wrong label ([arXiv 2401.01614](https://arxiv.org/html/2401.01614)). This is the closest published analogue to Lunatap's indexed list, and it won.
- **AppAgent** (Dec 2023): XML elements get numeric labels overlaid on the screenshot; the agent emits `tap(5)`. On 45 tasks/9 apps with a 10-step cap: GPT-4 raw action space 2.2%, simplified action space 48.9%, auto-explored docs 73.3%, demo docs 84.4%, hand-written docs 95.6% ([arXiv 2312.13771](https://arxiv.org/html/2312.13771)). Note the benchmark is self-made and tiny.
- **Mobile-Agent v1** (Jan 2024): screenshot-only; OCR for text targets, Grounding DINO + CLIP for icons; "solely relies on device screenshots without any system code". Mobile-Eval (10 apps × 3 instructions): success 0.91/0.82/0.82, completion 98.2%/90.9%/91.3%; the paper's text and table disagree on which column is which ([arXiv 2401.16158](https://arxiv.org/html/2401.16158)).
- **Mobile-Agent-v2** (Jun 2024): planning (text GPT-4), decision (GPT-4V) and reflection (GPT-4V) agents; perception via ConvNextViT OCR, GroundingDINO and Qwen-VL-Chat-Int4; claims "over a 30% improvement in task completion" over v1, on 10 instructions per category ([arXiv 2406.01014](https://arxiv.org/html/2406.01014)).
- **Mobile-Agent-v3 / GUI-Owl** (Aug 2025): Qwen2.5-VL 7B/32B. ScreenSpot-V2 92.8/93.2, ScreenSpot-Pro 54.9/58.0, AndroidWorld 66.4 (7B alone) and 73.3 (framework with 32B), OSWorld-Verified 29.4 (7B general) ([arXiv 2508.15144](https://arxiv.org/html/2508.15144)). This line moved from tool-based perception (v1/v2) to a native grounding model (v3).

## 2. Accessibility tree vs screenshot-only grounding

**AndroidWorld** (Rawles et al. 2024): 116 tasks, 20 apps, human 80.0% ([arXiv 2405.14573](https://arxiv.org/html/2405.14573)). M3A's element list is literally Lunatap's format: `UIElement(text=..., content_description=..., class_name=..., bbox_pixels=BoundingBox(...))` with an index, and the action JSON carries `index`.

| Agent | Input | Model | SR |
|---|---|---|---|
| M3A | a11y list only | GPT-4 Turbo | **30.6** |
| M3A | a11y list + SoM screenshot | GPT-4 Turbo | 25.4 |
| M3A | a11y list only | Gemini 1.5 Pro | 19.4 |
| M3A | a11y list + SoM | Gemini 1.5 Pro | 22.8 |
| SeeAct | SoM | GPT-4 Turbo | 15.5 |

Three seeds of the best config gave 27.6/26.3/33.2% (mean 29.0), so differences under ~5 points are noise. M3A took 3.9 min/task (2.5 min text-only). Later agents on the same benchmark: SeeAct-V with GPT-4o + UGround-V1-7B 44.0 ([UGround](https://arxiv.org/html/2410.05243)); GPT-4o + Aguvis-7B 37.1 ([Aguvis](https://arxiv.org/html/2412.04454)); UI-TARS-72B 46.6 ([UI-TARS](https://arxiv.org/html/2501.12326)); Agent S2 54.3 ([Agent S2](https://arxiv.org/html/2504.00906)); UI-TARS-1.5 64.2 ([README](https://github.com/bytedance/UI-TARS)); GUI-Owl framework 73.3; UI-TARS-2 73.3 vs OpenAI CUA-o3 52.5 ([UI-TARS-2](https://arxiv.org/html/2509.02544)). Caveat: these are vendor-run, different step budgets, and the leaderboard is a Google Sheet that does not verify submissions.

**OSWorld** (desktop) is the cleanest same-model comparison of observation spaces ([arXiv 2404.07972](https://arxiv.org/html/2404.07972)): GPT-4(V) a11y tree 12.24%, screenshot 5.26%, screenshot+a11y 12.17%, SoM 11.77%; GPT-4o 11.36/5.03/11.21/4.59; human 72.36%. The authors attribute SoM's weakness to "much more elements" (noise from marks) and to tasks needing coordinate-level precision.

**AndroidLab** (same model, XML list vs SoM): GPT-4o 25.36% vs 31.16%; Gemini 1.5 Pro 18.84% vs 16.67%; fine-tuned LLaMA 23.91% vs 10.14%; fine-tuned Qwen2(-VL) 19.57% vs 18.12%. No mode wins overall ([arXiv 2410.24024](https://arxiv.org/html/2410.24024)). **AndroidControl** used a11y only and states "best performance is still reported when using accessibility trees or HTML" (a literature claim, not a result) ([arXiv 2406.03679](https://arxiv.org/html/2406.03679)).

**Google Artemis**: the README claims "99%+ task completion" on "100+ multi-step tasks" across "20+ apps", names no model, date, method or paper; perception "Combines accessibility hierarchies and OCR with visual models for custom Canvas, Compose, and Flutter interfaces", targets "element indices when available, with coordinate and visual locating fallbacks"; Pro's Safety Net is "XML-first, pixel fallback"; Flash ~3–5 s/step, Pro ~15–40 s/step ([github.com/google/artemis](https://github.com/google/artemis)). Treat 99% as self-reported and not comparable to the paper numbers above.

Bottom line: an a11y list is at least as good as pixels for a general LLM chooser, and cheaper; screenshot-only wins only once the model is trained for grounding (section 3).

## 4. Frontier computer-use agents

- **Anthropic (Claude).** The tool returns clicks as pixel coordinates: "Coordinates are in screenshot pixels ... with the origin at the top left"; the integrator rescales. Guidance: 1024x768 or 1280x720 for desktop, "Avoid resolutions above 1920x1080"; a `zoom` action exists for dense UI; limits listed include "Claude sometimes acts as if its actions succeeded without explicitly checking", dropdowns/scrollbars being hard, and "Claude Sonnet 4.6 is more mechanically precise at clicking than Claude Opus 4.6" ([computer-use docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). Scores: Sonnet 4 42.2% and Sonnet 4.5 61.4% on OSWorld (Sep 29 2025) ([announcement](https://www.anthropic.com/news/claude-sonnet-4-5)); the Opus 4.8 post (May 28 2026) says "We made changes to how we run the OSWorld-Verified evaluation ... and have updated the Opus 4.7 score to 82.3%", with the 4.8 figure only in an image ([announcement](https://www.anthropic.com/news/claude-opus-4-8)). Methodology changed mid-series, so these are not one curve.
- **OpenAI CUA / Operator.** The system card: CUA "combines GPT-4o's vision capabilities with advanced reasoning through reinforcement learning. It interprets screenshots and interacts with graphical user interfaces", and "CUA's performance on OSWorld is currently at 38.1%, indicating that the model is not yet highly reliable for automating tasks on OS" ([system card PDF](https://cdn.openai.com/operator_system_card.pdf)). The API returns `{"type":"click","button":"left","x":405,"y":157}`; the current docs example models are `gpt-6.1-sol` with the `computer` tool and `gpt-6-astra` with code execution ([docs](https://developers.openai.com/api/docs/guides/tools-computer-use)). Third-party tables put CUA at 32.6 (50 steps) ([Agent S2](https://arxiv.org/html/2504.00906)), 36.4 ([UI-TARS README](https://github.com/bytedance/UI-TARS)) and CUA-o3 at 42.9 OSWorld / 52.5 AndroidWorld ([UI-TARS-2](https://arxiv.org/html/2509.02544)).
- **Google Project Mariner.** Dec 11 2024 post: "an early research prototype built with Gemini 2.0", understands "pixels and web elements like text, code, images and forms", acts through a Chrome extension, "83.5%" on WebVoyager, "not always accurate and slow to complete tasks today" ([blog.google](https://blog.google/technology/google-deepmind/google-gemini-ai-update-december-2024/)). No OSWorld/AndroidWorld number was ever published; the DeepMind model page no longer resolves, and reports that the project was folded into other products are secondary (not verified here).

All three ground by coordinates from a screenshot and rely on scale, trained precision and post-action screenshots rather than an element list. None of them is a cheap per-step component; they are the thing Lunatap's fast path is trying to avoid calling.

## 5. TypeSafe Jev and Cloudflare Clef: what the docs actually say

**Positioning.** "System One Models are a new class of AI model built for decisions inside software"; "Jev returns typed decisions with calibrated probabilities"; "Decisions, not strings" ([typesafe.ai](https://typesafe.ai/)). The docs say the models are not for generating text and not for "questions that need extended reasoning or that weigh several independent factors", which should be split into atomic questions combined in code ([docs](https://docs.typesafe.ai/)). Nothing in the docs positions them for GUI grounding; the closest items are Box, the OCR-bounding-box cookbook and "Cut the image into tiles and ask a Choice with the tiles as its options" ([images](https://docs.typesafe.ai/images.md)).

**Question types.** Choice (up to 255 options; option names *and* descriptions are sent to the model; `probabilities` sums to 1; `confidence` "computed from how probabilities is spread"; a "none of the above" option "may not work well in many use cases", use a companion Noul) ([Choice](https://docs.typesafe.ai/primitives/choice.md)); Noul (P(statement true)); Score; Box (Jev 1.14 only: edges as fractions 0–1, "A Box answer is always a box", one target per question, "A target a few dozen pixels wide in a very large image can be missed", "There is no recommended threshold yet") ([Box](https://docs.typesafe.ai/primitives/box.md)).

**Confidence.** "Confidence measures how concentrated the answer's probabilities are, which is different from the probability that the selected answer is correct"; thresholds should differ "depending on the consequences of getting it wrong"; for Choices inspect "the other probabilities or the top-to-second ratio" ([confidence](https://docs.typesafe.ai/confidence.md)).

**Known limitations (vendor).** "Jev does not count reliably"; "the order of a Choice's options can affect the answer, and Jev leans toward the option that comes first"; "Accuracy falls as the state grows with content unrelated to the decision"; semantic labels beat raw values (colour names vs hex) ([jaggedness](https://docs.typesafe.ai/model-jaggedness.md)).

**Limits and price (TypeSafe API).** Jev 1.14/1.13: 64k tokens per request, 32k per question; $0.042 per Mtok input, output free; images need the `TypeSafe-Danger-Zone-Images: true` header; "Images and Box questions aren't yet up to our standards to call ready for production"; PNG/JPEG, 16 MiB per file, each side 280–1568 px, 78,400–2,458,624 pixels, 32 MiB body, no fixed image count, images "never resized to fit" ([models](https://docs.typesafe.ai/models.md), [images](https://docs.typesafe.ai/images.md)). No latency or rate-limit numbers in the docs; the homepage's "0.114s vs 8.566s", "193.6x Faster, 444.6x Cheaper" chart is footnoted "based on workflows for System One tasks" and is marketing ([typesafe.ai](https://typesafe.ai/)).

**Cloudflare Clef (the model Lunatap uses).** `@cf/cloudflare/clef-flash`: "fast 9B multimodal decision model that turns a state and a schema of typed questions into decisions"; question types **noul, choice, score only (no Box)**; 1–64 questions; up to 4 images (PNG/JPEG/WebP), 4 MiB and 16 MP each, 8 MiB decoded, 13 MiB body; each image capped at 1,024 tokens after resizing, one token per 32x32 px block plus 3 markers; context 24,576 tokens; $0.038 per M input tokens, output free; no latency claim ([clef-flash](https://developers.cloudflare.com/workers-ai/models/clef-flash/)). `@cf/cloudflare/clef` is 27B, 65,536 context, $0.24 per M input ([clef](https://developers.cloudflare.com/workers-ai/models/clef/)). The Workers AI catalog lists no TypeSafe/Jev model ([catalog](https://developers.cloudflare.com/workers-ai/models/)). Derived, not stated: 1,024 tokens of 32x32 blocks is about one megapixel, so a 1179x2556 iPhone screenshot is downsampled by roughly 1.7x per side before Clef sees it; a 44 pt (132 px) icon becomes ~2–3 blocks.

## 6. Apple-side facts: what the XCUITest tree and Vision OCR give you

- **The tree is the accessibility tree.** UIKit header: `isAccessibilityElement` "default == NO / default on UIKit controls == YES / Setting the property to YES will cause the receiver to be visible to assistive applications"; `accessibilityElementsHidden` "Marks all the accessible elements contained within as hidden"; `accessibilityViewIsModal` "elements outside this view will be ignored. Only elements inside this view will be exposed" (`UIAccessibility.h`, iOS SDK in Xcode; [reference page](https://developer.apple.com/documentation/objectivec/nsobject-swift.class/accessibilityelementshidden)). So custom `UIView`s, CALayer-drawn controls, canvas/game views and anything behind a modal are absent unless the developer opted in. SwiftUI's `accessibilityElement(children:)` with `.combine` or `.ignore` collapses a row of controls into one element or drops them ([SwiftUI docs](https://developer.apple.com/documentation/swiftui/view/accessibilityelement(children:))); `accessibilityIdentifier` is described as the stable hook for UI automation, "to avoid inappropriately setting or accessing an element's accessibility label" ([docs](https://developer.apple.com/documentation/uikit/uiaccessibilityidentification/accessibilityidentifier)).
- **What WDA `/source` writes.** Attributes: `type, value, name, label, enabled, visible, accessible, x, y, width, height, index`; `hittable` only with `includeHittableInPageSource`; `index` is sibling position; a stability wait (`animationCoolOffTimeout`, default 2 s) runs first ([FBXPath.m](https://github.com/appium/WebDriverAgent/blob/master/WebDriverAgentLib/Utilities/FBXPath.m), [FBConfiguration.m](https://github.com/appium/WebDriverAgent/blob/master/WebDriverAgentLib/Utilities/FBConfiguration.m)). `visible` = cached snapshot attribute, else "any descendant visible", else a native query, else **NO** with a log line ([XCUIElement+FBIsVisible.m](https://github.com/appium/WebDriverAgent/blob/master/WebDriverAgentLib/Categories/XCUIElement%2BFBIsVisible.m)); `accessible` likewise defaults to **NO** when the native lookup fails ([XCUIElement+FBAccessibility.m](https://github.com/appium/WebDriverAgent/blob/master/WebDriverAgentLib/Categories/XCUIElement%2BFBAccessibility.m)). `snapshotMaxDepth` defaults to 50 (comment: "performance is acceptable up to 100"); `snapshotMaxChildren` defaults to INT_MAX ([FBConfiguration.m](https://github.com/appium/WebDriverAgent/blob/master/WebDriverAgentLib/Utilities/FBConfiguration.m)). Consequence: a `visible="false"` or `accessible="false"` in Lunatap's parser can be a lookup failure, not a fact, and deep SwiftUI trees can be truncated.
- **Vision OCR.** `recognitionLevel`: "Set this value to fast to prioritize speed over accuracy, and to accurate for longer, more computationally intensive recognition"; `.fast` "returns results more quickly at the expense of accuracy", `.accurate` "takes more time to produce a more comprehensive result" ([recognitionLevel](https://developer.apple.com/documentation/vision/vnrecognizetextrequest/recognitionlevel), [enum](https://developer.apple.com/documentation/vision/vnrequesttextrecognitionlevel)). The fast path boxes individual characters; the accurate path "tokenizes on whitespace"; results default to an English bias; `usesLanguageCorrection` costs time and `minimumTextHeight` defaults to 1/32 of image height ([guide](https://developer.apple.com/documentation/vision/recognizing-text-in-images), [minimumTextHeight](https://developer.apple.com/documentation/vision/vnrecognizetextrequest/minimumtextheight)). WWDC19: fast = character detector + small model, accurate = neural network over lines, "much broader support" for rotated/stylised text; language correction "does not come for free" and can turn "C001" into "cool"; the session gives **no** latency figures ([WWDC19 234](https://developer.apple.com/videos/play/wwdc2019/234/)). Apple publishes no accuracy numbers for either level.

## 7. Hybrid designs and where grounding fails

- **Propose with cheap perception, choose with a model** is the common pattern: OmniParser (detector + captioner + OCR → list → GPT-4V) lifted ScreenSpot from 16.2 to 73.0 ([OmniParser](https://arxiv.org/html/2408.00203)); SeeAct's ranked textual choices beat SoM by ~20 points ([SeeAct](https://arxiv.org/html/2401.01614)); Agent S2's Mixture of Grounding routes each action to a visual grounder (UI-TARS-72B-DPO), Tesseract text grounding, or structural grounding, raising OSWorld from 27.69→30.77 (15 steps) and 33.85→38.46 (50 steps) ([Agent S2](https://arxiv.org/html/2504.00906)).
- **Narrow before you ground.** ScreenSeekeR: a planner proposes regions, the grounder runs on crops, recursion until ~1280 px patches; OS-Atlas-7B goes 18.9→48.1 on ScreenSpot-Pro with no training ([ScreenSpot-Pro](https://arxiv.org/html/2504.07981)). GUI-Actor adds a verifier that picks among candidate regions ([GUI-Actor](https://arxiv.org/abs/2506.03143)).
- **Error analyses.** UGround: "planning errors are the dominant cause of failures across all benchmarks"; the most frequent is describing the wrong element; grounding errors "mostly come from idiosyncratic icons" ([UGround](https://arxiv.org/html/2410.05243)). SeeAct SoM: 54% hallucinated marks, 46% right box/wrong label ([SeeAct](https://arxiv.org/html/2401.01614)). AndroidWorld: perceptual (misreading a checkbox state), reasoning (believing text was already entered), missing knowledge, grounding (clicking the whole text field), plus a task that fails whenever the target needs horizontal scrolling ([AndroidWorld appendix](https://arxiv.org/html/2405.14573)). OSWorld: SoM degrades with many elements ([OSWorld](https://arxiv.org/html/2404.07972)). Anthropic's click-diagnosis table lists unscaled coordinates, small targets lost to downscaling, and wrong-element clicks from ambiguous instructions ([docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). Mobile-Agent-v2 added a reflection agent precisely because "ineffective" and "wrong page" outcomes were common ([Mobile-Agent-v2](https://arxiv.org/html/2406.01014)).
- The recurring failure classes are therefore: duplicates/ambiguous descriptions, icon-only targets, targets not in the current list (off-screen or off-tree), and misjudged state (already done / did not take effect). The first and last are chooser problems; the middle two are list problems no chooser can fix.

## Implications for Lunatap

Concrete options, each with the evidence behind it and a way to test it on the simulator trace set.

1. **Keep the indexed list as the primary grounding; it is the best-evidenced cheap design.** Evidence: M3A a11y-list 30.6 vs SoM 25.4 (same model), SeeAct choices 39 vs SoM 20 ([§2](#2-accessibility-tree-vs-screenshot-only-grounding)). Test: per-step grounding accuracy on a labelled set of ≥200 steps (not 40), split by target type (text row / icon / off-tree / off-screen).
2. **Treat Clef as a chooser, never as a grounder.** It has no Box; Jev's Box is preview and "always a box". Do not ask it for coordinates. Evidence: [clef-flash](https://developers.cloudflare.com/workers-ai/models/clef-flash/), [Box](https://docs.typesafe.ai/primitives/box.md).
3. **Shrink and order the option list before asking.** Vendor: first-option bias and distractor sensitivity; literature: SoM/choice accuracy falls with element count. Options: (a) pre-filter by text/type match and keep ≤15–20 options; (b) put the text-match candidate first *and* re-ask with a shuffled order on close calls (the docs' own consistency check); (c) keep one-line descriptions per option including position words and class. Test: accuracy and agreement rate under two orderings.
4. **Gate on P(option) and the top-to-second ratio, not `confidence`; pair with a Noul.** Evidence: [confidence](https://docs.typesafe.ai/confidence.md), [companion Noul](https://docs.typesafe.ai/patterns/companion-noul.md). The current `move` three-way Choice is the right shape; add "Is the control for `step` visible on screen?" as a Noul and require both. Test: calibration curve of P(top) vs correctness on the labelled set; choose thresholds per consequence (destructive taps stricter).
5. **Feed Clef crops, not only the full screenshot, when the target is small.** Clef sees ≤1,024 image tokens (~1 MP), so a full iPhone screenshot loses detail; the docs recommend asking on a small copy first and using tiles as Choice options. Option: send the full screenshot plus up to 3 crops around the top text/OCR candidates (4-image limit). Test: icon-target accuracy with vs without crops.
6. **Measure tree coverage and treat `visible/accessible=false` as unknown.** WDA defaults both to NO on lookup failure; depth is capped at 50. Metric: fraction of Vision OCR boxes with no overlapping tree element per screen; alert when high (custom views, SwiftUI combine). Option: raise `snapshotMaxDepth` on screens where OCR-only elements dominate, and include OCR-only boxes as first-class options (already done) with a distinct class so the chooser knows they are untyped.
7. **Add a local visual grounder as the fallback for off-tree targets instead of (or before) the LLM.** OS-Atlas-7B / UI-TARS-1.5-7B / GUI-Actor-7B all run locally and score 84–94 on ScreenSpot-v2 with mobile text >93%; ShowUI-2B is the small option (75.1 SS) ([§3](#3-dedicated-grounding-models)). This mirrors Agent S2's visual expert and Artemis's "visual locating fallbacks". Test: on steps where the fast path abstains, compare grounder-vs-LLM hit rate and latency on Apple-silicon inference. Check licences before shipping (UI-TARS Apache-2.0; OmniParser detector MIT; Ferret-UI weights unclear).
8. **Verify after acting, cheaply.** Anthropic's own caveat ("acts as if its actions succeeded") and Mobile-Agent-v2's reflection agent argue for a post-tap Noul on the before/after pair ("Did the screen change as `step` intended?") before the next step, which Clef can answer in the same request as the next `move`. Test: reduction in repeated/ineffective taps per task.
9. **Keep the safety net, but make its first check structural.** OSWorld/SeeAct show pixel-only verification is the weakest layer; XML-first with pixel fallback (as Artemis Pro does) is consistent with the evidence.
10. **Benchmark honestly.** There is no public online iOS benchmark; Ferret-UI's iPhone sets are static grounding, AndroidWorld is Android. Build a 50–100 task simulator suite with programmatic checks, report success, steps, seconds/step and $/task, run ≥3 seeds (AndroidWorld's spread was 26–33% for one config), and compare: LLM-only, text-match+Clef+LLM, and +local grounder.
